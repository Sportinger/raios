# 1. Current reality

The repository is past the packet's B1 baseline: B1.2c and B1.3 are verified closed. B2 must reuse those install/rollback mechanisms, but it must not confuse three different existing workspaces.

- The real AI transport exists. `seed-kernel/src/provider.rs` has `AgentRequest::{text,program}`, `RequestTarget::{Conversation,ProgramWorkspace}`, `submit`, and `poll`; `seed-kernel/src/openai.rs` has `submit_request`, `poll`, `perform_https_request`, `build_request_body`, and `extract_output_text`. It sends `store:false` requests to the hard-coded OpenAI Responses endpoint/model and returns the first `output_text` string.
- The transport is trust-gated, but its trust claim is deliberately narrow. `provider_trust::snapshot` and `can_attempt_openai_tls`, together with `openai_trust::OpenAiPinnedCertVerifier`, enforce the configured leaf/SPKI pin and TLS 1.3 P-256 CertificateVerify path. `OPENAI_PINNED_TLS_VERIFIER_METADATA` honestly says `pin_only_no_webpki_chain_validation` and `not_validated_stage0`; B2 must not call this WebPKI or trusted-time validation.
- A usable credential is mandatory. `provider::submit` returns `SubmitError::MissingApiKey` when the Vault/legacy RAM credential is unavailable; `provider_config::{api_key_set,set_api_key,init_default_config}` are the legacy RAM/build-time path. `seed-kernel/src/shell_host/context.rs::provider_state` renders exactly `Needs key` when `provider::Snapshot.api_key_set` is false. That is the current Genesis state and is a named live-B2 precondition, not a documentation nuisance.
- Provider export plumbing is only partly armed. `agent_protocol_provider::provider_minimal_context_evidence_for_runtime`, `emit_provider_context_export_denied`, and `emit_provider_context_export_authorized_selftest` build/check/audit bounded projections. However, `openai::build_request_body` attaches no context, `OPENAI_PROVIDER_CONTEXT_INJECTION_GATE` says `automatic_context_injection_disabled`, and the real `provider.context_export` still denies. This does not block B2.1's owner request, but it does block a truthful live B2.2 feedback loop.
- A provider answer already becomes an inert bounded RUIP draft. `console::submit_chat` routes `/build` to `submit_program_prompt`; `program_authoring_prompt` asks for `RAIOS_UI_SPEC_V1`; `program_workspace::note_provider_build_request` records the request; `main.rs` routes a `ProgramWorkspace` event to `program_workspace::accept_provider_answer`. That function accepts only `RUIP_BASE64:` canonical bytes or a valid `RAIOS_UI_SPEC_V1`, builds a typed `Program`, and keeps it inert. `program_workspace::Source::{Provider,Serial,Durable}` distinguishes live-provider, serial, and B1.3 reboot-restored drafts. `agent_protocol_program::emit_workspace` exposes the current draft through `program.workspace`; Genesis requires the existing pointer path before execution. This is a fast RUIP-program lane, not B2.1 source files.
- The durable source-file machinery also exists, but only behind serial/agent-protocol imports and edits. `project_workspace::{import_begin,import_file_begin,import_chunk,import_file_finalize,import_commit}` calls `raios_core::project_workspace::build_local_import` and `project_store::commit`. The core validates paths, case aliases, media types, quotas, blob hashes, sorted trees, parent links, and revision hashes. `project_store::commit` writes blobs first, the immutable manifest last, then reloads and compares the revision. `project_workspace::inspect`, `project_query::{read,search}`, and the corresponding protocol emitters make the files inspectable.
- `project_editor::{edit_begin,edit_file_begin,edit_chunk,edit_file_finalize,edit_delete,edit_diff,edit_commit,edit_discard}` already supplies exact-base RAM overlays and immutable child commits. It is suitable for later agent revisions after provider-answer parsing, not for parsing provider prose.
- `project_build::{begin,source_read,dependency_read,record_run,commit,receipts,verified_receipt_exact}` is existing W4 development scaffolding. It verifies an exact source/dependency snapshot and two reported output identities, but the compiler runs on the owner workstation and the receipt says `builder_attested_not_local_rebuild`/`independently_verified=false`. It is not on-device compilation and cannot close Vision station 4.
- `workspace_candidate_service::{prepare,approve_and_run_from_pointer}` is the existing W5 sandboxed candidate path. `agent_protocol_project_install::{emit_install_prepare,emit_install_signature,approve_from_pointer}` plus `project_app_autoload::run_boot_autoload` are the existing W6 install/reboot/rollback path B2.3 must reuse.
- Genesis already renders the composer hint `Ask anything, or /build <program>...`, the `AI connection` row, and the existing `[RUN]`/`[PERSIST]` states in `shell_host/genesis.rs::{draw_composer,draw_context}`. It has no source-project build-job state.
- Contrary to the packet's shorthand, there is no `project.workspace` method in the current dispatch table. The durable source surface is `project.inspect` plus `project.read`/`project.search`; `program.workspace` is RUIP-only. B2 should add a project-job view rather than overload the RUIP response.

Missing for B2: a source-file answer contract; a provider request target for it; exact answer/provenance binding; a system-owned job state; direct typed commit without synthesizing serial commands; a `project.workspace` view and Genesis source status; a verifier-feedback packet; a real authorized provider body attachment; iteration; and slow-lane orchestration. The live AI link additionally needs network, a usable API key, a configured positive pin-verifier path, and an available provider response.

# 2. B2.1 contract (the first implementable slice)

Capability sentence: an owner can ask for a project in Genesis and receive one bounded, inspectable, content-addressed source revision; no returned byte is signed, built, loaded, run, installed, or persisted as an executable.

End-to-end flow:

1. Make `/build <description>` the source slow-lane entry. Existing `console::submit_chat` calls NEW `console::submit_project_prompt`; NEW `console::project_authoring_prompt` asks for one exact response grammar. Preserve the current RUIP fast lane under explicit NEW composer spelling `/program <description>`, which still calls existing `submit_program_prompt`; retain raw `program.ask` compatibility. Do not guess the route from natural-language content.
2. The response grammar is NEW `RAIOS_SOURCE_FILES_V1`: exact header, one or more `file <base64-path> <base64-utf8-content>` lines, exact `end`, and nothing else. The provider does not declare classification, byte length, hashes, project identity, capabilities, or trust. raiOS forces every file to `Classification::LocalOnly`, derives a fixed media type from the validated path, rejects non-UTF-8/unknown path types for this first Rust/TOML source slice, and reuses `module_candidate_channel::decode_base64_chunk`.
3. `seed-kernel/src/provider.rs` adds NEW `AgentRequest::project`, NEW `RequestTarget::ProjectWorkspace`, and NEW `AnswerProvenance`. NEW `console::submit_project_prompt` passes that request to existing `provider::submit`; existing `provider::poll` returns the matching event. The provenance carries request-body/envelope hashes plus the observed verifier id/state/outcome, chain/time policies, and bypass flag. `seed-kernel/src/openai.rs` adds NEW `provider_answer_provenance` after the successful TLS/HTTP response; existing `openai::{submit_request,perform_https_request,poll}` carry it back without changing the answer bytes.
4. NEW `seed-kernel/src/agent_build_loop.rs` owns only B2 orchestration. NEW `derive_project_id` domain-hashes the exact owner request into a stable 16-byte id; NEW `note_provider_build_request` stores request id, project id, request hash, and phase; NEW `accept_provider_answer` requires the exact pending request and positive non-bypass live provenance; NEW `note_provider_error` closes the matching pending request; NEW `snapshot` exposes the current-boot phase honestly. A mismatched, late, duplicate, bypassed, or untracked answer cannot replace the last valid revision.
5. NEW `agent_build_loop::parse_answer` parses the bounded grammar and yields owned path/content pairs. It has no store, build, or runtime calls. NEW `media_type_for_path` is a fixed mapping, not provider authority. All quotas and path/collision rules are rechecked by the core builder.
6. `raios-core/src/project_workspace.rs` adds NEW `RevisionAction::AgentAnswer`, NEW `agent_project_id`, and NEW `build_agent_answer`. `build_agent_answer` accepts the system-derived project id, the exact currently loaded parent (or none), and borrowed `SourceFile`s; it reuses the existing private revision builder, blob encoder, tree hash, revision hash, and manifest encoding. The action label is `agent_answer`, never `owner_local_import` or `agent_overlay_commit`.
7. `seed-kernel/src/project_workspace.rs` adds NEW `commit_agent_answer`. It loads the current parent with existing `project_store::inspect`, calls NEW core `build_agent_answer`, calls existing `project_store::commit`, reloads through that existing readback check, and returns the exact revision. It never calls an `import_*` string parser and never forges owner provenance.
8. `main.rs` adds the NEW `ProjectWorkspace` answer/error branches and calls the loop functions; NEW `console::write_project_outcome` reports request/project/revision/file counts without printing source. The ordinary conversation target and RUIP target remain unchanged.
9. `agent_protocol_project.rs` adds NEW `emit_workspace`; `agent_protocol.rs` adds the NEW exact `project.workspace` route. It returns loop phase, pending request id, project id, latest revision/tree/file facts, answer provenance, `scope=current_boot` for job state, and the existing QEMU-store posture for committed files. Existing `project.inspect`/`project.read` remain the authoritative durable file readers. Existing `program.workspace` remains RUIP-only and must be unchanged in the B2.1 proof.
10. `shell_host/genesis.rs::draw_context` reuses `draw_short_hash` and adds NEW `draw_agent_build_status` for `[SOURCE] Requesting`, `[SOURCE] Ready`, or `[SOURCE] Rejected`, with project/revision short hashes. B2.1 shows no run/install approval button for source files.

Pinned invariants:

- Inert means all protocol/job results say `signing_attempted=false`, `builder_attempted=false`, `load/execution/install/promotion_authorized=false`; no candidate intake, Wasm instance, W6 preview, RECLOG/ARTSTOR executable record, or service inventory mutation occurs.
- Source-file commitment to the existing disposable QEMU structured workspace is allowed; it is not installation. `physical_media_supported=false` remains true, and B2.1 adds no physical-media path.
- Identity is recomputed from exact decoded bytes and sorted validated paths. Provider-supplied hashes do not exist in the grammar. Store reload/reparse must reproduce every blob, tree, parent, and revision hash before success is shown.
- Live ingestion requires positive pinned/WebPKI state as reported by the actual verifier and rejects the development bypass. Even when positive, source authority remains `untrusted_agent_candidate`; pin-only/no-time limitations stay visible and confer no execution authority.
- Physical approval and W6 are out of B2.1. The source revision merely lands inert.

# 3. B2.2 sketch

The final loop is: exact source revision -> system-selected check/build/test -> immutable result with evidence locators -> bounded classified feedback -> provider proposes a complete child source set -> raiOS reparses/recomputes/rechecks -> either another child or a locally verified candidate. Provider text never supplies `passed`, a receipt, a grant, or an approval.

Reuse `project_store::load`, existing `project_build` snapshot/receipt checks, `project_editor`'s immutable-parent model, and `workspace_candidate_service::snapshot`. Add NEW `project_build::verify_source_revision`, a narrow wrapper over existing `snapshot_exact`, so the loop can run deterministic local source preflight without opening a workstation build session. Add NEW `agent_build_loop::{record_verifier_result,build_feedback_packet,submit_feedback_request,accept_revision_answer}` only when each step has a real caller.

The smallest provable slice is deliberately preflight-only: a fixture agent answer commits a revision missing `Cargo.lock`; NEW `verify_source_revision` returns the system-owned `build_cargo_lock_missing` result bound to that revision; a bounded fixture feedback packet cites the check id/revision/reason; a second fixture answer becomes an immutable child containing the missing file; the same verifier passes. The first revision remains readable. This proves result -> agent -> revision -> re-verification without executing code or pretending the owner-workstation compiler is on-device.

A live B2.2 request is blocked today by provider export, not merely by the API key. Before sending feedback, NEW `provider::submit_scoped_project_feedback` and NEW `openai::build_request_body_with_context` must consume a single-use positive decision from existing `raios_core::scoped_provider_export::evaluate_provider_export_gate`, bind the final body hash, apply an explicit field allowlist/redaction/token budget, append the durable export audit, and mark `context_attached_to_provider_body=true`. Until that positive path exists, fixture iteration is test infrastructure and B2.2 remains partial. Raw local-only source, logs, stdout, secrets, hardware facts, and unclassified text must stay out.

The existing W4 `BuildRun` stores exit/output hashes but not actionable stdout/stderr bytes, and its receipt is workstation-attested. Later feedback may cite that honest tier and W5 runtime facts, but cannot call them an on-device test. B3 supplies the real on-device compiler/test producer; B2 only builds the safe feedback/iteration control plane around evidence the system actually has.

# 4. B2.3 sketch

NEW `agent_build_loop::LoopPhase` grows monotonically through `requesting_source`, `source_ready`, `verifying`, `revision_needed`, `verified_source`, `awaiting_build_evidence`, `candidate_ready`, `awaiting_run_approval`, `tested`, `awaiting_install_approval`, `installed`, or an exact denied phase. NEW `agent_build_loop::Snapshot` is the single Genesis projection; it holds ids/hashes/status only, never source text or authority tokens.

The development-era lane is:

1. `/build` order -> B2.1 provider answer -> visible `project.workspace`/Genesis source status.
2. Local preflight/agent revisions -> visible check status and evidence locator.
3. Existing W4 scaffold uses `project_build::{begin,source_read,dependency_read,record_run,commit}` and returns an honestly labeled workstation-attested receipt. Genesis must show `Workstation build scaffold`; it must not say on-device build. B3 later replaces the producer, not the receipt/verification boundary.
4. Existing `workspace_candidate_service::prepare` binds exact project/revision/receipt/candidate facts. The existing Genesis pointer route calls `approve_and_run_from_pointer`; no serial or agent call can substitute. This is the constitution-required approval before the current-boot sandbox run.
5. Only a healthy exact run may advance to the existing W6 path: `agent_protocol_project_install::{emit_install_prepare,emit_install_signature}` creates the signed preview, serial approval stays denied, and the final Genesis pointer invokes existing `approve_from_pointer`. Existing W6 store/autoload/rollback machinery remains the only install path.

This deliberately reuses the proven `docs/plans/b12c-plan.md` and `docs/plans/b13-plan.md` shape: an inert candidate, a physical W5 run approval, then a separate signed W6 install approval; no alternate install path is added.

Thus "approval at the end" means the final W6 install approval is shown only after source/build/test evidence is visible. It does not erase the earlier W5 physical approval required before any candidate test execution. Combining those two clicks would change the constitution/B1 contract and is out of scope.

1. **B2.1a, answer-to-files seam (key-free).** Extend existing `project-workspace`. Add NEW harness-only `agent_build_loop::accept_test_fixture`, NEW `agent_protocol_project::emit_agent_answer_fixture`, and NEW `project.agent_answer_fixture`; enable the fixed answer only on the existing disposable QEMU store and label it `test_infrastructure=true`, `answer_origin=test_fixture`, `provider_trust_positive=false`. Both it and the live handler delegate to NEW private `agent_build_loop::accept_answer`. Predicates: exact two-file parse/commit; host-recomputed blob/tree/revision hashes; action `agent_answer`; `project.workspace`, `project.inspect`, and `project.read` agreement; malformed/base64/path/case/quota/late-answer failures preserve the last revision; reboot reparse reproduces the source revision; `program.workspace` unchanged; zero build/load/run/install/W6/RECLOG/ARTSTOR/service effect. This proves the real ingestion/store seam, not a live AI connection.
2. **B2.1b, Genesis and real-provider integration.** Extend existing `genesis-ui` for `/build` routing, pending/ready/rejected source status, `/program` RUIP compatibility, and absence of a source run button. Extend `vm-harness/openai-direct-smoke.ps1` with NEW `-ExpectProjectWorkspaceAnswer` for the required live closure run: usable local key image, real e1000/DNS/TLS/HTTPS, positive pinned trust, `ProjectWorkspace` target, structurally valid source answer, and inert committed files. 3. **B2.2a, one proof-carrying revision (fixture, partial B2.2).** Extend existing `project-workspace`: revision 1 fails NEW local preflight for exact `build_cargo_lock_missing`; the feedback packet binds project/revision/check/reason and excludes source/secrets; fixture revision 2 has parent=revision 1 and passes; revision 1 remains byte-readable; neither check nor iteration builds/runs/installs. When real scoped feedback export is implemented, extend existing `provider-memory` with final-body hash binding, field classification/redaction/budget, single-use authorization, durable export audit, exact attachment, and smuggle/trust-downgrade negatives before attempting live iteration.

Harness rules for all three slices:

- The new `project.*`/existing `program.*` results use the established `raios.agent.v0` `body.result` carve-out: assert top-level `v`, then fields under `body.result`; do not invent a nested result schema assertion. Evidence-envelope families remain root `raios.evidence_response.v1` and do not use `body.result`.
- Marker readers accept the observed CR-CR-LF ending and use tolerant line search plus `TrimEnd()`.
- Do not assert a sub-200 ms event through the shared 200 ms wait grid. Wait for semantic markers or use a safely larger bound; no new B2 predicate needs wall-clock timing.
- Codex workers write kernel/harness packets; the orchestrator compiles/packages and runs the focused profile. A worker packet must not claim a kernel build it cannot perform.

# 6. Risks + open questions

- **AI-connection precondition.** Current Genesis says `AI connection: Needs key`; live B2 additionally needs network and positive supported pin verification. **Recommendation:** prove B2.1 parsing/storage with the explicitly labeled fixture so normal development is key-free, but require a separate pinned-SPKI live report before claiming the AI link or closing B2.1b. A mock answer proves no DNS/TLS/API/provider behavior.
- **Existing `project_*` versus new answer code.** Putting provider grammar/state into `project_workspace` would mix an external trust boundary with generic storage; synthesizing `project.import_*` strings would create a second parser and false owner provenance. **Recommendation:** NEW `agent_build_loop.rs` owns request state, answer grammar, provenance, and phases; `project_workspace::commit_agent_answer` is the only new bridge; core canonicalization and `project_store` stay authoritative and provider-blind.
- **`/build` already means RUIP.** Silent heuristics would make owner intent ambiguous. **Recommendation:** reserve `/build` for the B2 slow lane and expose the existing bounded fast path explicitly as `/program`; keep `program.ask` for protocol compatibility and update the composer hint.
- **Provider feedback export is disabled.** Embedding local test text in `program_authoring_prompt`/ordinary user text would bypass ADR 0004 and existing gates. **Recommendation:** B2.2 cannot go live until the final scoped export authorization, exact-body attachment, classification/redaction/budget, and durable audit are wired; fixture iteration stays labeled partial.
- **Provider trust is pin-only today.** A successful pin does not establish WebPKI chain or trusted time. **Recommendation:** record exact verifier metadata with each live answer, reject bypass for source ingestion, and keep `untrusted_agent_candidate` independent of transport tier.
- **Durability scope.** `project_store` is a disposable QEMU structured store and `physical_media_supported=false`. **Recommendation:** use it because it is the real W1 mechanism, prove readback/reboot there, and make no Surface/production workspace-persistence claim.
- **Build-site honesty.** W4 is owner-workstation scaffolding and B3 on-device compilation is missing. **Recommendation:** B2.3 may orchestrate and display W4 evidence, but it must stop at `awaiting_build_evidence` without it and must never claim the self-build loop is closed before B3.
- **Approval count.** W5 execution and W6 installation are distinct authority changes. **Recommendation:** keep two physical, one-shot, stale-checked approvals and show them as separate phases; do not optimize clicks by weakening the constitution.
- **Answer grammar/size.** OpenAI output is bounded by `MAX_OUTPUT_TOKENS`, while the workspace allows 48 KiB. **Recommendation:** B2.1 accepts one complete bounded response only and fails closed without replacing the prior revision; add chunked/multi-response authoring only after a real project exceeds the response budget.
- **Fixture leakage.** A hidden fallback could make "AI-connected" tests lie. **Recommendation:** fixture origin is explicit in every response/status, unavailable outside the disposable-store test configuration, never produces positive provider trust, and never satisfies the live B2.1b predicate.
