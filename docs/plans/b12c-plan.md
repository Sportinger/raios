# 1. Contract

The starting state is the accepted B1.2b `GRANTED_CANDIDATE_CURRENT_BOOT_ACTIVATION`: the W7 bytes are still the only retained bytes, the exact W7 receiver identity and M6 grant/attestation are bound under the consumed activation challenge, `svc.dev.granted_candidate` is running, and its current-boot `run_count` is exactly 1. Installation must not run it again.

End-to-end order:

1. Preserve the accepted activation as a NEW private `ApprovedActivation` in `seed-kernel/src/granted_candidate_service.rs`. Existing `emit_load` -> `prepare_activation` -> `derive_activation_binding` -> `approve_and_run_from_pointer` still performs the first, physical M6 run. `approve_and_run_from_pointer` additionally captures the already-computed activation challenge, pre-load inventory hash, successful load event/generation, and exact `ActivationBinding`; it creates no durable effect and does not set `State.promotion`.
2. The host sends existing `project.install_prepare sha256:<b12b_activation_challenge>`. Existing `emit_install_prepare`/`prepare_install` in `seed-kernel/src/agent_protocol_project_install.rs` dispatches that hash to NEW `prepare_granted_candidate_install` when it matches `granted_candidate_service::approved_install_envelope`; the existing workspace/W4 branch remains unchanged.
3. The W7 source enters W6 as a NEW typed `raios_core::project_install::GrantedCandidateInstallEnvelope`, sealed by NEW `seal_granted_candidate_install_envelope` and checked by NEW `validate_granted_candidate_install_envelope` in `raios-core/src/project_install.rs`. It contains the service id, candidate hash/length, B1.2b activation challenge, M6 grant and attestation-reference hashes, W7 invocation/receipt hash, all three receiver/catalog candidate-binding hashes, generation, `auto_start=true`, and `trust_tier=dev_key_not_owner_sealed`. It contains no `ProjectInstallEnvelope`, `ProjectInstallIntent`, encoded build receipt, project id/revision, or W4/W5 workspace binding. `project_install_store::persist_physical_install` is therefore not called and no `ProjectInstallCommit` or `PROJECT_INSTALL_COMMIT` marker is fabricated.
4. W6 reuses existing `ProjectInstallAction { kind: Install, authority: PhysicalOwner, service_id: svc.dev.granted_candidate, install_envelope_sha256: Some(<new envelope hash>), ... }`, existing `approval_hash`, `authority_evidence_hash`, `install_action_signature_payload_sha256`, and the existing `PROJECT_INSTALL_PREVIEW` marker. The action's sequence is the next RECLOG sequence and its predecessor is the current RECLOG tail, so any intervening append makes the preview stale.
5. The host reads `action_signature_message_sha256` from the prepare response and signs that digest with the existing `ota-tools` binary `dev-promotion-signer`, invoked only through existing `vm-harness/shadow-vm-smoke-support.ps1::New-ReliableDevPromotionSignatureHex`. This is the existing development signing chain. It is a second W6 signature over the install action, distinct from the earlier M6 attestation-reference signature.
6. The host sends existing `project.install_signature <DER-hex>`. Existing `emit_install_signature` -> `accept_signature` -> `verify_promotion_authority_signature` -> `seal_install_action` arms the W6 preview. The host then sends `project.install_approve`; existing `emit_install_serial_approval_denied` must return `project_install_physical_pointer_approval_required`, with the signed preview still pending and zero writes.
7. The owner makes a second Genesis pointer click. Existing `ShellHost::handle_pointer_interaction` checks `agent_protocol_project_install::pending_physical_approval` before the granted/workspace run approvals and calls existing `approve_from_pointer`. Its NEW granted-candidate branch calls NEW `validate_current_granted_install_preview`, re-verifies the sealed action/signature and exact approved B1.2b binding, rechecks the RECLOG tail, and calls NEW `granted_candidate_service::install_approved_from_pointer`.
8. `install_approved_from_pointer` creates the same `PromotionRecord` that the existing durable M6 path expects, but from the pre-load inventory hash and load event captured at the first click. It sets no new loader state and does not call `load` or `start`. It reuses existing `append_promotion_transaction(Promote)` -> `durable_store::append_promotion_transaction`, then existing `artifact_store::persist_promoted_artifact`. Thus the candidate bytes are written once through the existing ARTSTOR blob-frame path and both the promote transaction and artifact-persist link are appended through the existing RECLOG path. Only after both readbacks succeed does it retain `State.promotion` and the NEW fixed-size `SignedInstallAuthorization`.
9. On success the kernel emits the NEW marker (one line, CRLF):

   `GRANTED_CANDIDATE_INSTALL_COMMIT result=accepted physical_approval=genesis_pointer source_kind=w7 candidate_sha256=sha256:{candidate} w7_receipt_sha256=sha256:{receipt} activation_approval_sha256=sha256:{activation} install_envelope_sha256=sha256:{envelope} install_action_sha256=sha256:{action} promotion_transaction_sha256=sha256:{promotion_frame} artifact_persist_frame_sha256=sha256:{persist_frame} generation={generation} sequence={sequence} run_count=1 trust_tier=dev_key_not_owner_sealed durable_writes=true reason=granted_candidate_installed`

   Every denial uses the same field order and emits:

   `GRANTED_CANDIDATE_INSTALL_COMMIT result=denied physical_approval=genesis_pointer source_kind={w7|none} candidate_sha256={sha256:{candidate}|none} w7_receipt_sha256={sha256:{receipt}|none} activation_approval_sha256={sha256:{activation}|none} install_envelope_sha256={sha256:{envelope}|none} install_action_sha256={sha256:{action}|none} promotion_transaction_sha256=none artifact_persist_frame_sha256=none generation={generation} sequence={sequence} run_count={run_count} trust_tier=dev_key_not_owner_sealed durable_writes=false reason={reason}`

10. On a clean reboot, NEW `repromotion::run_provider_autoload` is called from `main.rs` after structured-store initialization and existing `project_app_autoload::run_boot_autoload`. It requires a success-marked Normal boot, resolves the newest valid promote/unpromote transaction for `svc.dev.granted_candidate`, requires the exact linked artifact-persist record, and calls existing `reverify_record`. That reuses `reverify_record_only`, `artifact_store::read_verified_artstor_payload`, `reverify_persisted_artifact`, `repopulate_reverified_references`, `wasm_runtime::validate_module_bytes`, `module_candidate_intake::retain`, and the existing recovery-only `emit_repromotion_load`/`emit_repromotion_start` wrappers. NEW `restore_reverified_install_authorization` restores the W6 authorization before those wrappers append/reload, so both M6 and W6 signatures remain in provenance.
11. Provider autoload emits the NEW marker:

   `GRANTED_CANDIDATE_PROVIDER_AUTOLOAD result={accepted|denied} phase={autoloaded|not_installed|rolled_back|denied} reason={reason} posture={Normal|Probation|Safe|PersistenceUnavailable} candidate_sha256={sha256:{candidate}|none} promotion_transaction_sha256={sha256:{promotion_frame}|none} artifact_persist_frame_sha256={sha256:{persist_frame}|none} m6_reverified={true|false} w6_signature_verified={true|false} loaded={true|false} running={true|false} run_count={run_count} cross_reboot_proven={true|false}`

   `phase=autoloaded` requires both signatures reverified, `loaded=true`, `running=true`, boot-local `run_count=1`, and `cross_reboot_proven=true`. No serial command is needed.
12. Rollback reuses existing `emit_rollback_preview`, `emit_rollback_apply`, `rollback_apply`, `service_inventory_projection_hash`, and `append_promotion_transaction(Unpromote)`. The response must show cleanup, exact inventory-hash restoration, and a readback-verified unpromote RECLOG frame. A second apply is denied. A third boot resolves the newer unpromote as `phase=rolled_back`, performs no byte intake/load/start, emits no guest log, and leaves the service absent. For this one-version provider install, rollback means durable removal/tombstoning, not a fictional previous version.

Kernel functions reused, beyond those named in the steps: `granted_candidate_service::{pending_approval,approval_preview,loaded_snapshot,record_activation_source_binding,emit_response,secure_attention_drop,build_promotion_record}`, `artifact_store::{current_boot_reclog_scan,artifact_persist_records_from_reclog}`, `durable_store::{promotion_transaction_payload_bytes,promotion_transaction_append_denied}`, and `repromotion::{emit_repromotion_run,reverify_and_load_record}`. NEW kernel functions are exactly: `granted_candidate_service::{approved_install_envelope,validate_approved_install_envelope,install_approved_from_pointer,restore_reverified_install_authorization,emit_install_commit_marker}`, `agent_protocol_project_install::{prepare_granted_candidate_install,current_granted_install_cursor,validate_current_granted_install_preview}`, `durable_store::validate_signed_install_authorization`, and `repromotion::{run_provider_autoload,resolve_granted_candidate_install,emit_provider_autoload_marker}`.

# 2. Invariants

- W7 remains the sole candidate-byte ingress for the B1.2c positive proof. W6 receives hashes and authorization only; ARTSTOR receives the bytes already held by `module_candidate_intake`. There is no workspace copy, project-build copy, second loader, alternate blob writer, or alternate RECLOG appender.
- Serial may prepare and submit the development signature, but cannot install or run. `module.load_ephemeral` remains prepare-only; `service.start` remains denied; `project.install_approve` remains denied. No new agent-protocol method maps to `install_approved_from_pointer`, `emit_repromotion_load`, or `emit_repromotion_start`.
- The M6 run click and W6 install click are separate, one-shot approvals with different challenges. The first is consumed before W6 can be prepared; the second cannot run the candidate. A stale preview, changed evidence, changed candidate, changed RECLOG tail, secure-attention drop, or replay denies before a write.
- B1.2b bytes and semantics stay byte-identical: the existing activation response/marker field set is unchanged; the first click still produces one run; load/start replay stays denied; stale binding stays denied; pre-install RECLOG/ARTSTOR/install/autoload/rollback effects remain zero.
- No W4 project receipt is synthesized. W7 provenance is labeled `receipt_kind=w7_acquisition`; `w4_project_receipt_present=false`; workspace W6 continues to use its real `ProjectInstallEnvelope` and receipt.
- Every durable authority fact is provenance-bound in the existing `raios.promotion_transaction.v0` typed record: M6 signature/reference, B1.2b activation challenge and W7 receiver/receipt fields, W6 envelope/action/digest/signature/physical-approval fields, candidate/service/generation, inventory rollback plan, and prior RECLOG tail. The ARTSTOR blob is authorized only by the linked promote frame; the artifact-persist RECLOG frame links both.
- Durable append is fail-closed. A promote without its exact artifact-persist frame, a blob without its RECLOG link, a bad readback, or a newer malformed transaction never falls back to an older install. Retry requires a fresh prepare, signature, and second physical click.
- Autoload is allowed only on a success-marked Normal boot. Safe, PersistenceUnavailable, Probation, missing/invalid store, missing W6 provenance, signature failure, or a newer unpromote produces no retain/load/start authority.
- Rollback is provable twice: the live inventory returns to the captured pre-load hash and a verified unpromote frame becomes the newest service decision; the following boot resolves it and does not resurrect any older promote/artifact record.
- Recovery `emit_repromotion_load`/`emit_repromotion_start` remain private wrappers with no direct serial route. Existing `agent repromotion.run` and recovery load-by-hash may reach the same `reverify_record` only after durable-record selection and full re-verification; B1.2c adds no bypass.

# 5. Risks and open questions

- `ProjectInstallAction` has inherited field names (`install_envelope_sha256`, `previous_commit_sha256`) but its signature ceremony is otherwise source-neutral. Recommended resolution: reuse it unchanged, set the envelope hash to the typed W7 envelope and the predecessor to the actual RECLOG tail, expose `install_source=granted_candidate`, and never emit a project commit. Renaming/generalizing W6 types is outside B1.2c and adds migration risk.
- Existing `emit_repromotion_load` uses durable effects and therefore appends a fresh promote/artifact-persist pair on every successful re-promotion/autoload. Recommended resolution for B1.2c: preserve this existing, already-tested path rather than create a second loader mode; make the newest-transaction resolver authoritative and record the bounded append-only capacity/GC issue explicitly for later storage work. Never silently overwrite or reuse occupied ARTSTOR space.
- A crash can leave a valid promote frame without its artifact-persist link, or an ARTSTOR blob without the link frame. Recommended resolution: latest decision wins and incomplete latest install denies autoload with no fallback; require a newly signed/physically clicked retry. Do not attempt repair or orphan reclamation here.
- The W6 development key remains `dev_key_not_owner_sealed`. Recommended resolution: keep that trust tier in every response/record/marker and use only `dev-promotion-signer`; do not imply owner-key custody.
- Rollback has no prior installed provider version in this slice. Recommended resolution: define and test it as durable removal (newer unpromote tombstone plus boot-3 absence). Version fallback requires a real later multi-version install record, not a fabricated predecessor.
- Automatic provider autoload and existing serial `agent repromotion.run` share `reverify_record`. Recommended resolution: both must call the same newest-transaction resolver; the automatic path additionally requires success-marked Normal posture. Keep the serial method for diagnostics/recovery compatibility but prove it cannot bypass W6 provenance or an unpromote.
