# B2 implementation notes

## B2.1a foundation

- Capability: a fixed key-free answer can become one inert, inspectable, content-addressed Rust/TOML source revision in the disposable QEMU workspace.
- The loop recomputes the request hash and project identity from the exact owner request; identity is `SHA-256("raios.agent_project_id.v1" || u64_le(request_len) || exact_request_bytes)`, truncated to 16 bytes by the core helper.
- `build_agent_answer` uses the existing revision builder and forces `local_only`; its shared path mapper derives only `text/rust` and `text/toml` and rejects non-UTF-8 content or other path types.
- The parser has one bounded-response ceiling only. The core builder remains authoritative for file/project quotas, path, case-alias, duplicate, sorting, blob, tree, parent, revision, and manifest checks.
- `commit_agent_answer` uses the existing inspect -> build -> blobs-first/manifest-last commit -> reload/compare store path and never enters the serial import parser.
- The fixture has a fixed request, request id, and two-file answer. It arms only an idle current-boot loop; replay is therefore untracked and cannot create a child revision accidentally.
- Fixture availability is enforced by the only commit backend: `open_disposable_qemu_store_port`; outside that configuration the commit returns `project_qemu_store_missing` and no answer is accepted.
- Fixture provenance binds the exact answer byte length/hash and is always `answer_origin=test_fixture`, `test_infrastructure=true`, and `provider_trust_positive=false`.
- `project.workspace` describes current-boot job state; `project.inspect` and `project.read` remain the durable file readers. `program.workspace` is unchanged.
- `writes_persistent_state=true` on fixture success means source records in the disposable QEMU structured store only; every executable/build/load/run/install/promotion field remains false.
- `project_overlay.rs` gained the compile-required exhaustive `AgentAnswer` rebuild arm so later W2 edits can verify this base through the same core builder.
- `note_provider_error` and the private shared `accept_answer` seam are present, but no live provider target, provenance, handler, console route, Genesis UI, build, runtime, approval, install, RECLOG, ARTSTOR executable, or service-inventory path is wired.
- No Cargo, rustc, build, or test command was run; the orchestrator owns compilation and VM evidence for this worker packet.

## B2.2a foundation

- Capability: a key-free fixture can now carry one system-computed source-preflight failure into an exact immutable child revision and re-run the same preflight over that child; it still cannot compile, test, run, install, or export anything.
- `verify_source_revision` stays in `seed-kernel/src/project_build.rs` because `snapshot_exact` and the exact disposable-store/dependency loads live there. The two-outcome source-shape predicate is the public cross-crate `raios_core::project_build::source_preflight` helper so the missing-lock and manifest-plus-lock cases have host tests without opening a kernel build session.
- The verifier is a deterministic local source preflight, not a compiler or test runner. It records `project.source_preflight.v1`, the exact revision/tree hashes, the system-selected reason, and `passed|failed`; provider text supplies none of those fields.
- The existing B2.1a fixture is revision 1 and intentionally lacks `Cargo.lock`, so its exact preflight reason is `build_cargo_lock_missing`. The child fixture is a complete three-file answer with the same `Cargo.toml` and `src/main.rs` plus a fixed `Cargo.lock`, so its exact preflight reason is `source_preflight_ok`; the existing source mapper now admits only the exact root `Cargo.lock` addition and classifies it as `text/toml`.
- `build_feedback_packet` stores only four cited values: check id, revision SHA-256, tree SHA-256, and reason. The protocol classifies the packet `local_only` and reports source/secret/log/unclassified bytes absent; no provider submission path consumes it.
- `accept_revision_answer` accepts only the fixed fixture, requires the tracked failed verifier result and matching feedback packet for the exact parent, arms a fixture-only child request, and delegates parsing/building/commit/readback to the existing private `accept_answer` seam.
- `commit_agent_answer` now requires the caller's exact expected parent instead of discovering and silently adopting whatever revision is current. A mismatch denies before commit; revision 2 therefore has parent exactly revision 1.
- `project_store::load_revision` reads an immutable manifest by exact project/revision identity. Before a child commit, the child route reparses and hash-validates revision 1's source blobs; failure consumes the request without a write. A successful child therefore carries a guaranteed parent-readback result plus both lineage entries.
- New `raios.agent.v0` body-result routes are `project.verify_revision`, `project.feedback_packet`, and `project.revision_answer_fixture`; `project.workspace` also exposes the current verifier result, retained feedback packet, and revision lineage. All build-session/compiler/test/run/load/install/W6/executable-record/service-mutation fields remain false.
- B2.2 remains partial: scoped feedback export, live provider submission, W4 compilation, B3 on-device compilation, W5 execution, W6 installation, and Genesis UI are deliberately not wired.
- No Cargo, rustc, build, test, or VM command was run; the orchestrator owns compilation and focused VM evidence for this worker packet.

## B2.2 live scoped export

- Capability: `project.feedback_submit` can queue one deliberate OpenAI request whose provider body receives the exact failed-revision feedback packet only after positive post-TLS export authorization and a verified durable pre-write audit; ordinary conversation, RUIP, and B2.1b project requests still attach no context.
- The new entry points are `agent_protocol_project::emit_feedback_submit`, `agent_build_loop::submit_feedback_request`, `provider::submit_scoped_project_feedback`, `openai::submit_scoped_project_feedback`, `openai::build_request_body_with_context`, and `memory_store::record_live_provider_export_audit`. `agent_build_loop::accept_provider_feedback_answer` sends the response through the unchanged private `accept_answer` seam with the exact failed revision as its required parent.
- The gate input is mapped directly to the authoritative `evaluate_provider_export_gate`: `method=provider.context_export`; `profile=provider_minimal`; the actual post-handshake `trust.state.as_protocol()` and TLS-bypass bit; the exact four-record public allowlist result; record count `4`; budget `1000`; estimated tokens `ceil(canonical_packet_json_bytes/4)`; the canonical packet SHA-256; destination `provider.openai.responses`; a complete verifier/decision snapshot predicate; and an audit-binding SHA-256 over request id, packet hash, final body hash, final envelope hash, destination, trust state/evidence, and bypass posture. An unexpected request target maps to the evaluator's exact `method_not_provider_context_export` denial instead of inheriting the scoped method.
- The candidate body uses only documented Responses fields: the fixed system direction is `instructions`, and the canonical four-record packet is the `input` string; no private top-level API parameter is invented. It is deterministic so its final SHA-256 can enter the gate/audit binding, but it is not selected for transmission and no attached-context envelope is created before the evaluator returns `performed=true`. After that decision, the kernel appends a unique per-request `raios.memory_record.v0` `export_audit` through the existing RECLOG gauntlet and requires performed append, sequence/payload evidence, frame/readback SHA-256 equality, and successful reparse. Only then does it mark the authorization consumed, construct `context_attached_to_provider_body=true`, record the current-boot request/export bindings, and expose the body to the HTTPS writer. The hash is checked again over the exact body immediately before the write.
- Single use is structural: a queued scoped request moves `Ready -> Taken` once when HTTPS processing claims its authorization, and the authorization's consumed bit is set only after verified durable append. Reusing either state fails as `single_use_export_authorization_consumed` / `OPENAI SCOPED FEEDBACK AUTHORIZATION ALREADY CONSUMED`; another export requires another `project.feedback_submit`, post-TLS snapshot, gate decision, request id, envelope, and durable record.
- Authoritative gate denials retain the evaluator's exact reasons: `missing_method`, `method_not_provider_context_export`, `missing_profile`, `profile_not_provider_minimal`, `missing_trust_state`, `trust_dev_bypass_not_positive`, `trust_state_not_positive`, `packet_contains_non_public_record`, `missing_packet_record_count`, `missing_budget_tokens`, `missing_packet_estimated_tokens`, `packet_exceeds_token_budget`, `missing_audit_packet_hash`, `missing_audit_destination`, `missing_audit_trust_snapshot`, and `missing_audit_binding_hash`. Local post-gate failures are `durable_export_audit_append_failed` and `final_provider_trust_downgraded_before_write`. These paths never select or send the context body and report `context_attached_to_provider_body=false`, `provider_write=not_attempted`.
- What may leave is the fixed system instruction plus exactly four packet records, each explicitly classified `public`: system check id, failed revision SHA-256, failed tree SHA-256, and system reason code. The current public allowlist is deliberately exact: `project.source_preflight.v1`, `build_cargo_lock_missing`, and nonzero revision/tree hashes.
- What cannot leave through this path: source bytes, file paths, logs, stdout, secrets, hardware facts, unclassified text, provider-supplied pass/fail, receipts, grants, approvals, classification, or identity. Model/max-output/store fields remain ordinary transport metadata; the API credential remains confined to the existing redacted Authorization-header path.
- A conforming revised answer reuses B2.1b ingestion with `RevisionAction::AgentAnswer`, `answer_origin=live`, exact-parent readback, and trust derived from the real response provenance. Core parsing still recomputes project/tree/revision identity, forces every source file `LocalOnly`, and leaves the child `untrusted_agent_candidate`; provider text receives no authority. No build, compiler, test, run, load, install, W6, promotion, physical-media, executable-record, or service-inventory mutation path is added.
- Trust remains honestly pin-only (`pin_only_no_webpki_chain_validation`, trusted time not validated) even though the core evaluator also recognizes a future `webpki_verified` state. No WebPKI or trusted-time claim was added. The code/current cursor and the B2.1b live-proof section are authoritative where older plan prose still describes live B2.1b as pending.
- Implementation status: source-wired and left for orchestrator compilation/live proof. This worker ran no Cargo, rustc, formatter, build, test, VM, provider request, install, or promotion command and makes no compile or runtime claim. The separate VM-harness packet remains untouched.

## B2.2 live harness

- `openai-direct-smoke.ps1 -ExpectScopedFeedbackExport` is mutually exclusive with the existing direct-provider modes and reuses the B2.1b key+pin image, disposable C1 structured-store disk, valid-a BOOTCTL persist disk, network readiness waits, `project.ask`, positive pinned-cert/SPKI transport, `Get-AgentResponseJson`, terminal source parser, and redacted failure diagnostics. With the switch absent, the conversation, pinned-trust, pin-mismatch, and `-ExpectProjectWorkspaceAnswer` flows retain their prior commands and assertions.
- Round trip 1 sends the same plain two-file Rust-project description and requires `PROJECT SOURCE READY request=<r1> ... files=2 inert`. `project.verify_revision` must record `outcome=failed`, `reason=build_cargo_lock_missing`, check `project.source_preflight.v1`, and the exact r1 revision/tree hashes; the merged protocol deliberately has no `passed` field. `project.feedback_packet` must be `local_only` with exactly the four cited properties and all source/secret/log/unclassified inclusion flags false.
- `project.feedback_submit` must return `status=started`, `accepted=true`, reason `provider_feedback_request_started`, a new r2 id, `export_method=provider.context_export`, `profile=provider_minimal`, four fields, no submit-time attachment, and `provider_write=not_attempted`. Round trip 2 then requires one new `openai: TLS 1.3 established` plus `openai: TLS provider trust verified: pinned_cert|pinned_spki`, with no `tls_certificate_verification_bypassed`.
- Exact positive r2 markers are `OPENAI_SCOPED_PROJECT_FEEDBACK_EXPORT {"status":"authorized","reason":"authorized_provider_export_public_only_audited",...}`, `OPENAI_PROVIDER_REQUEST_ENVELOPE` with source `project.feedback_export` and `context_attached_to_provider_body:true`, `OPENAI_PROVIDER_REQUEST_BINDING` plus `OPENAI_PROVIDER_EXPORT_AUDIT_BINDING` with `satisfies_current_boot_export_gate:true`, `positive_export_authorization:true`, and `automatic_context_injection=deliberate_scoped_feedback_only`, then `OPENAI_SCOPED_PROJECT_FEEDBACK_SENT` with `provider_write=performed`. The authorization must carry non-null durable sequence/payload evidence and exact durable reason `authorized_memory_record_append_readback_reparse_verified`; the kernel emits it only after the `raios.memory_record.v0` `export_audit` append, frame/readback hash equality, successful reparse, and post-append rescan.
- The host reconstructs the merged kernel's canonical `provider_minimal` packet and exact OpenAI body (`gpt-5.4`, fixed scoped-feedback instruction, escaped four-record input, 8192 output tokens, `store=false`) and compares both SHA-256 values with the r2 authorization/envelope/binding/sent markers. That proves only check id, r1 revision hash, r1 tree hash, and `build_cargo_lock_missing` entered the packet; marker lines are also rejected if they contain the raw description, `src/main.rs`, `Cargo`, `Content-Length`, or `Authorization: Bearer`.
- A conforming r2 must be an `agent_answer`/`live`/positive-trust/`local_only`/`untrusted_agent_candidate` child whose parent and first lineage entry are r1 and whose `parent_revision_readback_verified` bit is true. A grammar rejection must leave r1 as the exact latest readable two-file revision. After a conforming child, a second `project.feedback_submit` must deny exactly `agent_revision_feedback_packet_mismatch`, and the `OPENAI_DIRECT_REQ` count must not advance.
- Single-use semantics (resolved): after a grammar-rejected r2, r1's failed verifier result and feedback packet are RETAINED on purpose — `project.workspace` exposes them so the owner can see exactly what was exported (transparency). Single use is therefore per AUTHORIZATION, not per packet: each `project.feedback_submit` mints its own authorization that consumes a fresh positive gate decision + durable audit and produces exactly one export; a deliberate second submit would be a NEW independently-gated+audited export of the same public data, which is plan-compliant (b2-plan section 3: "another export requires another project.feedback_submit ... gate decision ... and durable record"), not a leak of new data. The harness proves this honestly: on a committed child it sends a second submit and asserts `agent_revision_feedback_packet_mismatch` with no new provider request; on a grammar rejection it asserts exactly one durably-audited scoped export left for the authorization (`OPENAI_DIRECT_REQ` total == 2) and does NOT send a second submit (which would legitimately export again). A future optional hardening could consume the packet per export to require a fresh failed-revision cycle, at the cost of the workspace transparency.
