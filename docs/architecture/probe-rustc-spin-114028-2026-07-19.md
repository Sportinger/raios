# Probe: rustc spin in function 114028

Date: 2026-07-19

## Result

Function 114028 is the wasi-libc/musl internal lock primitive `__lock`, from
`libc-top-half/musl/src/thread/__lock.c`. It is not a rustc algorithm and it is
not `__cxa_guard_acquire`.

The function polls one caller-supplied, 32-bit lock word `L` and reads the
signed, 8-bit musl gate `__libc.need_locks` at decimal address **26080269**
(`0x018df40d`). For an uncontended lock the concrete success predicate is:

```text
M8s[26080269] == 0
    => return without touching L

or, when M8s[26080269] != 0:

M32[L] == 0
    => cmpxchg32(L, expected=0, replacement=0x80000001)
       returns 0, stores 0x80000001, and __lock returns
```

There is an important evidentiary boundary: the supplied profile resolves the
current function, not the instruction offset or `local0`. It therefore proves
that execution was resumed in function 114028 for almost all fuel quanta, but
it does **not** reveal which call site supplied `L`. Static code narrows the
pre-WASI startup path to two especially relevant concrete words:

- **26079912 (`0x018df2a8`)**: wasi-libc's `getcwd`/current-working-directory
  lock. It is used by `__wasilibc_find_relpath_alloc`, `getcwd`, and the
  LTO-inlined `chdir` path. The latter calls `malloc` (function 113875) at
  `0x1edd06a` immediately before acquiring this lock at `0x1edd0bd`.
- **26079916 (`0x018df2ac`)**: wasi-libc's preopen-table lock. Function 113914,
  `__wasilibc_populate_preopens`, calls `__lock(26079916)` at `0x3f800ce`; its
  next external operation would be import 25, `fd_prestat_get`, at
  `0x3f800f2`. Stopping in that acquisition exactly explains zero WASI calls.

Both words lie in the proven BSS zero range and should initially be zero.
**26079916 is the strongest zero-WASI call-site match, but the runtime evidence
does not distinguish it from the earlier 26079912 acquisition.** A claim that
one of these addresses was actually observed would exceed the measurement.

This changes the diagnosis. In correct single-threaded execution, no spawned
thread, clock, or host call is needed to make this lock progress. Either
`need_locks == 0` elides it, or the running main thread's first compare-exchange
acquires a zero word. If raiOS is genuinely looping inside 114028, the state is
already inconsistent with the measured single-thread execution or the
interpreter is replaying/failing a compare-exchange or continuation boundary.

### Source-equivalent reconstruction

Modulo compiler unrolling and 32-bit wrapping arithmetic, the body is:

```c
void __lock(volatile int *L) {
    int need = __libc.need_locks;
    if (!need) return;

    int current = a_cas(L, 0, INT_MIN + 1);
    if (need < 0) __libc.need_locks = 0;
    if (!current) return;

    for (unsigned i = 0; i < 10; i++) {
        int expected = current < 0 ? current + INT_MAX : current;
        int old = a_cas(L, expected, expected - INT_MAX);
        if (old == expected) return;
        current = old;
    }

    current = atomic_fetch_add_via_cas(L, 1) + 1;
    for (;;) {
        if (current < 0) {
            __wait(L, 0, current);
            current += INT_MAX;
        }
        int expected = current;
        current = a_cas(L, expected, expected | INT_MIN);
        if (current == expected) return;
    }
}
```

Function 114029 is the paired `__unlock`: for a negative lock word it CAS-adds
`INT_MAX`, turning the uncontended `0x80000001` back into zero, and notifies one
waiter only when the old state was not exactly `0x80000001`.

## Why zero host calls and zero `atomic.wait` are possible

`__lock` never makes a WASI call. All of its loads, stores, and CAS operations
touch guest linear memory directly.

Zero `memory.atomic.wait32` further distinguishes its paths:

1. The ten optimistic attempts and the waiter-registration loop contain only
   loads and compare-exchanges.
2. The final loop calls function 114031 only when its local `current` is
   negative. A nonnegative sequence of failed CAS results loops without ever
   entering `__wait`.
3. Function 114031 first performs a finite bounded poll (100 value checks in
   the emitted two-check, 50-iteration form). With the null waiter-count
   pointer passed by `__lock`, an unchanged aligned word then reaches
   `memory.atomic.wait32` at `0x3f8c1ba`. Stable negative contention that is
   correctly resumed should therefore eventually increment the atomic-wait
   counter.

In a correct single logical thread, a stable CAS cannot fail forever when its
observed old value is immediately reused as the expected value. Thus a genuine
zero-wait infinite loop inside these CAS regions requires at least one of:

- the compare-exchange result/store contract is violated on the real shared
  memory path;
- the saved instruction pointer, operand stack, locals, or memory backing is
  replayed/restored inconsistently at a fuel boundary;
- the lock word is being changed by an unobserved actor (contradicted by the
  stated single-thread measurement unless the host itself changes it);
- `__wait`'s finite spin is restarted at each boundary before reaching its
  wait instruction.

There is no source-level musl branch where "single-threaded" means "spin".
Single-threaded is the opposite: `M8s[26080269] == 0` returns immediately. A
corrupted nonzero `need_locks` merely enables the locking code; another defect
or an orphaned held word is still required for endless progress failure.

## Who is supposed to write the state

The writers visible in the module are:

- `__lock` itself writes a free `L` to `0x80000001` (or another negative
  encoded held state).
- `__unlock` (114029) releases `L`; under real contention this is executed by
  whichever pthread currently owns the internal lock.
- `pthread_create` (114041) changes `M8[26080269]` to `1` at `0x3f8ced3` when
  the thread count changes from zero, immediately before its sole
  `wasi:thread-spawn` call at `0x3f8cedd`; on spawn failure it restores zero at
  `0x3f8cf39`.
- `wasi_thread_start` (114055) writes `255` (signed `-1`) at `0x3f8dbbb` when
  the last worker exits. The next `__lock` acquisition clears that transition
  state to zero.

The measured `spawns=0` rules out a spawned worker as the necessary writer in
this window. Starting from the zero-filled BSS, `need_locks` should stay zero
and an internal lock should be elided. Even if it were legitimately enabled,
the candidate cwd/preopen locks are acquired by the running main thread; their
normal writer is that same thread's successful CAS followed later by
`__unlock`. A clock or init writer is not involved.

If the observed word is already negative and only a nonexistent worker could
release it, that state is an orphan created by replay, stale memory restoration,
or corruption—not a normal wasi-libc startup dependency.

## Host-side fix hypotheses and falsification

### H1 — `LOCKSTEP-CMPXCHG`: real shared-memory CAS/resume defect

Instrument the interpreter only while current function is 114028. For every
`i32.atomic.rmw.cmpxchg`, record:

```text
round, tid, Wasm byte offset, effective L,
before, expected, replacement, returned_old, after
```

The generic kernel fix, if a violation appears, is to make the real
shared-memory implementation perform one indivisible operation: load old;
store the wrapped replacement iff old equals expected; push old; advance the
instruction pointer exactly once. The shared memory backing and operand stack
must survive fuel park/resume unchanged.

Falsification: for 64 consecutive hot rounds, every tuple satisfies
`returned_old == before`, `after == replacement` exactly when
`before == expected`, otherwise `after == before`, and the Wasm offset advances
past each successful CAS. That would rule out H1 and direct attention to the
caller/lock state rather than the atomic primitive.

The vendored implementation is statically correct and the existing
`atomics_rmw` conformance test covers success, failure, old-value return,
wrapped replacement, and equal fuel charge. H1 therefore specifically targets
the real module's shared backing plus continuation integration, not the
source-level formula in isolation.

### H2 — `PHANTOM-NEED-LOCKS`: stale/corrupt libc thread state

At every fuel boundary record:

```text
current function+instruction, local0 L,
M8[26080269], M32[L], M32[26079912], M32[26079916]
```

Also log every store to address 26080269 with its current function/offset. With
no thread-spawn call, a transition from zero to `1` or `255` without one of the
three statically identified writer sites proves host memory replay/corruption.
The implementable fix is to keep one persistent shared linear-memory backing
for the job and never restore an older page image when swapping fuel or
continuations.

Falsification: the byte remains zero for the whole trace and 114028 executes
past its `br_if` at `0x3f8be7d`. That combination would disprove stale
`need_locks` and instead expose wrong load/control-flow or profiler attribution.

### H3 — `FORWARD-FUEL-BLOCK`: no-progress fuel replay

Record the exact compiled instruction pointer and required `ConsumeFuel` debit
at each 114028 suspension. If every round parks before the same instruction
because its debit exceeds the installed quantum, the pump must carry fuel debt
or grant at least the next static block cost. This is generic and does not
special-case libc addresses.

Falsification: the installed rustc quantum is 1,000,000 and the recorded debit
fits, or the instruction pointer advances across rounds. Given the small
control-flow blocks in this function, this hypothesis is lower probability but
cheap to exclude.

### Decisive next run

One capped 64-round run with the H1/H2 fields would resolve the missing facts:

```text
RAIOS_RUSTCLOCK round=<n> func=114028 off=<wasm-off> L=<addr>
  G=<i8> before=<u32> expected=<u32> replacement=<u32>
  returned=<u32> after=<u32>
```

Expected healthy single-thread result is either an immediate gate return with
`G=0`, or, for a deliberately enabled zero lock, exactly one
`0 -> 0x80000001` CAS returning zero. A negative test should initialize `L` to
a nonmatching value and prove a failed CAS returns that old value without a
store. This simultaneously proves the positive predicate and its boundary.

## Honest limits

Proven statically:

- 114028 is wasi-libc/musl `__lock`; 114029 is `__unlock`.
- The complete lock-state algorithm, its 8-bit gate address, its one 32-bit
  caller-supplied word, every CAS predicate, and its only callee are as stated.
- The concrete cwd and preopen lock addresses and their source objects/call
  sites are as stated.
- Stable negative contention through function 114031 reaches an atomic wait
  after a finite spin; a correct single-thread CAS has a progress path without
  any host actor.
- The profiler is function-resolution only and records current function again
  on executor reconstruction.

Proven at runtime only by the supplied serial record:

- execution remained attributed to function 114028 for the dominant retained
  sample count;
- zero WASI calls, zero atomic waits, zero spawns, and no stdout occurred before
  the round limit.

Not proven:

- the instruction offset inside 114028;
- the runtime value of `local0`, `need_locks`, either lock word, or any CAS
  operand/result;
- which direct caller entered the hot invocation. In particular,
  `L=26079916` is a strong pre-WASI inference, not a measurement; 26079912
  remains a viable earlier/later cwd-lock site;
- that compare-exchange, memory persistence, or fuel replay is actually faulty.
  These are falsifiable hypotheses, not claimed runtime observations.

Accordingly, the requested single concrete *observed* address cannot honestly
be recovered from a function-index-only profile. The report gives the exact
predicate for `L`, the concrete statically bounded addresses, and the minimal
measurement needed to close that last gap.
